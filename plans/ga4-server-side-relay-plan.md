# GA4 First-Party Server-Side Collection Relay (stape.io-style, Next.js/Vercel)

Status: **APPROVED WITH MINOR NOTES (round 3, Critic) — PENDING APPROVAL** (Architect: 3 rounds, held; Critic: 3 rounds, CRITICAL→5 MAJOR→0 MAJOR/7 minor — see Changelog)
Mode: RALPLAN-DR (deliberate — compliance/PII in scope)

## RALPLAN-DR Summary

### Principles
1. Ship stateless-first — state lives in cookies/env vars, not a database, until proven necessary.
2. Never claim delivery guarantees the platform doesn't provide (best-effort v1; explicit, separate path to at-least-once later).
3. Compliance and PII safety are load-bearing, not optional — every event passes consent + PII gates before it leaves the server.
4. Prefer supported/documented integration points (GA4 Measurement Protocol v2, `gtag` `server_container_url`) over reverse-engineered ones (`/g/collect`, minified-bundle rewriting).
5. Retry and dedupe ship together or not at all — a retry layer without dedupe silently corrupts customer analytics.

### Decision Drivers (top 3)
1. Vercel's execution model (stateless, time-boxed functions, no long-lived process) rules out an always-on self-hosted sGTM deployment (Option D) within the user's stated Vercel constraint — it does **not** rule out Option B on statelessness grounds (a container config snapshot can be fetched-and-cached per serverless instance same as sGTM caches it per boot); Option B is rejected separately, on the sandboxed-template-engine cost (see Option B's invalidation rationale).
2. GA4 Measurement Protocol returns 2xx even on malformed/rejected payloads — nothing about "does it work" can be trusted without validation-first design and the `/debug/mp/collect` endpoint in tests.
3. Compliance exposure (GDPR Consent Mode v2, GA4 ToS ban on PII) makes consent-gating and PII filtering must-have for v1, not deferrable hardening.

### Viable Options

**Option A — Purpose-built first-party GA4 collection relay + resilience layer (CHOSEN)**
Single-tenant, installable package of config-injected route-handler factories that a site owner mounts into their own Next.js app on their own domain. Translates browser events to GA4 Measurement Protocol v2, owns first-party `client_id`/session cookies, gates on Consent Mode v2, validates payloads, and adds a service-worker-backed retry/dedupe layer for resilience.
- Pros: buildable by one person; matches what stape.io customers actually pay for (first-party hosting, cookie longevity, resilience) rather than Google's own tag-engine; fits Vercel's stateless model naturally (cookie *is* the state); genuinely same-origin (no third-party data processor, likely better ITP/cookie story than a CNAME-based vendor).
- Cons: lower fidelity than real sGTM (no automatic `session_start`/`first_visit`, no Google Signals, no automatic attribution); does not replace sGTM for teams needing a multi-destination tag/trigger/variable engine.

**Option B — Full sGTM container clone (tag/trigger/variable engine + config UI) — REJECTED**
Invalidation rationale (revised per Architect antithesis): the real multi-year cost is the *sandboxed template-execution engine and template marketplace*, not container statelessness — a container config snapshot can be fetched-and-cached per serverless instance same as sGTM caches it per boot, so "fights the stateless model" was not the true blocker. Rejected instead on: building a general-purpose sandboxed expression/template engine is out of reach for a solo project and duplicates a product Google already ships. This does NOT rule out a versioned, declarative (non-code, non-sandboxed) event-mapping config file — see Principle-guardrail note below.

**Option C — Multi-tenant SaaS from day one — REJECTED**
Invalidation rationale: pulls in auth, custom-domain provisioning, encrypted per-tenant secret custody (a customer's GA4 `api_secret`), billing, and cross-tenant isolation testing before the core value is even proven. Adds a materially different security/compliance posture (data processor for other people's users) with no v1 benefit. Can be layered on top of Option A's stateless core later **only if** M1 modules take an explicit, injected config object rather than reading ambient globals — see Implementation Steps M1 (package/factory restructure, applied per Architect review).

**Option D — Self-host Google's official sGTM container image, reverse-proxied same-origin via Next.js rewrites — REJECTED (added per Critic review — the strongest alternative not in the original draft)**
This deploys Google's real sGTM Docker image on an always-on container host (Cloud Run/Fly/a small VM) and reverse-proxies it through the Next.js app's own origin, which would deliver Option A's first-party-cookie/no-third-party-processor advantage *and* the full tag/trigger/variable engine Option B was rejected for being too expensive to build. This is a genuinely different, credible option — not a restatement of B (nothing is rebuilt) or C (still single-tenant). Invalidation rationale: (1) it requires an always-on process, which conflicts with the "Next.js/Vercel" framing the user asked for and reintroduces the operational surface (container host, uptime, scaling) that a Vercel-only relay was meant to avoid; (2) reverse-proxying sGTM's own request/response cycle through Next.js rewrites has its own latency and streaming-response correctness problems that would need their own spike before being trusted; (3) the resilience layer (retry/dedupe/offline queue/SW) — this project's actual differentiator over stock sGTM — is additive on top of *either* Option A or Option D, so choosing D over A wouldn't avoid *that* work; it would, however, genuinely avoid rebuilding `mp-client`/`cookies`/`consent`/`validate` (1.1-1.4), since sGTM already does the equivalent of those. Reason (1), the Vercel-only constraint, is dispositive on its own and doesn't need reason (3) to carry more weight than it does. Option A remains chosen because it's deployable entirely within the user's stated Vercel constraint; Option D is recorded here (rather than omitted) specifically so a future reviewer doesn't have to re-derive why it wasn't picked.

## Requirements Summary

Build a self-hosted, single-tenant **first-party GA4 collection endpoint** (not a "GTM container" — deliberately dropping that framing to avoid scope creep toward Option B), distributed as an **installable package of config-injected route-handler factories** (per Architect review — a hardcoded app-local route cannot satisfy the ad-blocker path-configurability requirement below, and is not actually "your own version of a product" for anyone but the author) plus a client SDK and a resilience service worker. The package is installed by a site owner into their own Next.js app; **same-origin, same-app deployment (not a separate subdomain/project) is a hard requirement**, not an option — it is what makes the first-party-cookie/ITP advantage in the ADR true. It:
- Accepts browser-originated analytics events, mints/reads a first-party `client_id` and session cookie (compatible with an existing `_ga` cookie if present), and forwards to GA4 Measurement Protocol v2.
- Enforces Consent Mode v2 (`ad_storage`, `analytics_storage`, `ad_user_data`, `ad_personalization`) before setting any persistent identifier or forwarding any event with one attached.
- Validates every payload against MP's documented limits and a PII deny-list before forwarding (MP does not report processing failures — 2xx is returned regardless).
- Binds requests to a browser context that has loaded the site (signed short-lived token bound to origin, checked alongside an Origin allowlist — this is **request provenance, not visitor authentication**: any client can obtain a valid token simply by loading the page first, same posture as stock client-side GA4/`gtag`) and rate-limits abuse using a per-installer-configured key.
- Ships a client SDK that resolves capture-time identity (`client_id`/`ga_session_id` + signature) **once per page load** — the first event (a load-time `page_view`, not an unload event, so it has no need for `sendBeacon`'s unload guarantee) is always sent via `fetch keepalive` specifically because its response is readable; every subsequent event on that page reuses the cached identity and follows the normal transport chain (`sendBeacon` primary at unload → `fetch keepalive` → IndexedDB queue) — and a companion service worker whose job is **retry/delivery resilience**, not primary event capture — promoted to a capture role only if a Playwright spike confirms SW `fetch` interception reliably sees unload-time beacons (open per analyst finding; default assumption is "unreliable," see Pre-mortem #1).
- Explicitly excludes in v1: a tag/trigger/variable config engine or UI, `/g/collect` reimplementation, non-GA4 destination fan-out (Meta CAPI etc.), multi-tenancy, and gtag.js bundle rewriting.

## Pre-mortem (3 failure scenarios)

1. **SW promoted to "capture layer" without validation.** Team ships service-worker `fetch` interception as the primary way to catch unload-time `sendBeacon` calls without running the Playwright cross-browser spike first. It turns out unreliable (this is the single hardest case for SW interception — the case the project most wants to fix). The highest-value event on the site (the exit `page_view`) keeps getting lost, and the project fails to beat plain client-side GA4 on the one metric that justified building it.
   - Mitigation: SW's role defaults to **retry-only** (queued from the main thread on `fetch`/`sendBeacon` failure or offline detection). Promotion to "capture layer" is gated behind the spike in Implementation Step 0 passing, not assumed.

2. **Retry ships before dedupe.** Schedule pressure lands the IndexedDB retry queue in a release before the dedupe store. A retried event that actually succeeded the first time (response merely lost in transit) gets sent twice. GA4 silently accepts it (2xx, no error) — the corruption is invisible until someone notices inflated event counts weeks later, and by then customer trust in the numbers is gone.
   - Mitigation: Principle 5 enforced as a project rule — retry queue and dedupe store (client-generated `event_id` + server-side dedupe TTL store) merge in the *same* PR/milestone. CI blocks merging a retry-capable client SDK without a corresponding dedupe check in the collect route's test suite.

3. **Consent gating bug leaks a persistent identifier under denial.** A logic error sets or forwards the first-party `client_id` cookie, or emits identity in the response body, even when `analytics_storage: 'denied'` — for example a fallback code path that runs before the consent check (this scenario materialized for real during round-2 review, where the identity-JSON response initially had no consent condition attached at all — see Critic finding C1, fixed in 1.3/1.7). This is a live GDPR exposure that unit tests miss because they test the consent function in isolation, not the actual bytes on the wire.
   - Mitigation: consent gating gets a standing **network-level** contract test (assert on the actual `Set-Cookie` and outbound MP payload, not just the function's return value) that runs on every PR touching `packages/ga4-relay/src/**`, not only on PRs that touch the consent code itself.

## Acceptance Criteria

**Must-have (v1, milestone M1 unless noted):**
1. A `page_view` posted to the installer-mounted collect route (e.g. `/api/ga4/collect` — the path is installer-chosen, see 1.7) is forwarded to GA4 MP, and the same payload sent to `/debug/mp/collect` returns an empty `validationMessages` array.
2. A first request with no cookie present receives `Set-Cookie` with a `v1:`-prefixed UUID `client_id` (per 1.2); a second request from the same browser sends the **same, unprefixed** `client_id` to MP (per 1.2's strip-before-forward rule).
3. On a site already running `gtag`, the relay's `client_id` equals the `<random>.<timestamp>` portion of the existing `_ga` cookie when present, rather than minting a second identity.
4. Two events 5 minutes apart share one `ga_session_id`; two events 31+ minutes apart get a new `ga_session_id` and an incremented `ga_session_number`.
5. `ip_override` in the outbound MP payload equals the **platform-set** `x-vercel-forwarded-for` header exclusively, and never equals the serverless function's own egress IP, and never falls back to parsing the client-supplied `x-forwarded-for` (spoofable — client-controlled input must never feed `ip_override`). Tested against a mock MP server, since this is not observable from the real endpoint.
6. A request carrying `analytics_storage: 'denied'` (interpretation locked: **drop the event entirely** — zero outbound MP calls, never a fresh-random-`client_id` cookieless ping, since GA4 MP v2 requires `client_id` on every call and there is no conforming way to send "no identifier") results in: no *persistent* `Set-Cookie` (a `Max-Age=0` **deletion** header is explicitly not a persistent `Set-Cookie` and does not fail this criterion — see AC31), zero outbound MP calls, and **no identity or signature in the collect response body** — asserted at the network level on all three surfaces, not just via the consent function's return value.
6a. A request with **no consent object present at all** is treated as fully denied (default-deny), with the same three-surface network-level assertions as AC6 — an absent signal must never be treated as implicit grant.
6b. An event captured while offline and later flushed from the IndexedDB queue (M2) carries the `client_id`/`ga_session_id` that were current **at capture time**, not whatever the cookie holds at flush time — verified by: go offline mid-session, wait past the 30-min session window, come back online, and assert the flushed event's session id matches the pre-offline session, not a newly minted one.
7. A request whose `Origin` is outside the configured allowlist gets `403` and produces zero outbound MP calls.
8. A request with a missing/invalid/expired signed token gets `401`; CI builds the client bundle with a **canary value** substituted for `apiSecret`/`tokenSecret` (never the real production secret, which would itself be a log/artifact leak vector) and greps the bundle for the canary — build fails if found. Enforced additionally at the type/bundler level via the `./client` export condition excluding any module that imports `token.ts`/`mp-client.ts` (see M8/1.13).
9. Posting the same client-generated `event_id` twice produces exactly one outbound MP call (M2, once dedupe store exists).
10. A batch of 40 events is split into two MP requests of ≤25 events each.
11. An event name over 40 characters is **rejected outright** (dropped, `dropped-permanent` counter incremented) — not truncated, since truncation silently merges distinct event names in GA4 reporting; the same rule applies to param values over 100 chars.
12. With the network offline, an event is written to the IndexedDB queue; once `online` fires, it's delivered with `timestamp_micros` set to enqueue time (±1s), not send time (M2).
13. A queued event older than 48h is dropped, not sent (M2).
14. (M2) Registering the resilience service worker on a page that already runs another service worker (e.g. `next-pwa`/Workbox) does not deregister or shadow it.
15. (M2) The installer-mounted SW route (path installer-chosen, e.g. `/ga4-sw.js`) is served with `Cache-Control: no-cache` (or `max-age=0`).
16. (M2) Flipping the kill-switch config causes the SW to stop running (via AC28's main-thread `unregister()`, and secondarily via the SW's own `activate` check) within one page load, and the host site continues functioning normally.
17. Added median latency at the collect endpoint is under 50ms in M1 (rate limiting only, 1 `Store` round trip), **measured against a deployed (non-local) function, including the Upstash round trip, excluding only the MP forward itself** (which runs in `after()`); re-measured against a 65ms budget once M2 lands (rate limiting + dedupe, 2 `Store` round trips) so the criterion doesn't quietly break when the second `Store` operation is added. The browser never blocks on the response (`sendBeacon`/`keepalive` fire-and-forget). Baseline is zero added latency (i.e. this is an absolute ceiling, not a delta against an undefined comparison point).
18. Relay p99 latency from request-in to MP-request-issued is under 2s at 50 RPS load-test (burst; not a steady-state SLA), measured via a load-test harness that distributes distinct `kid`-keyed tokens across simulated virtual users (or uses an explicit test-only rate-limit override) so AC29's per-`kid` threshold doesn't trip the load test itself — see AC29. **Measurement method**: since the MP forward runs in `after()` (after the client-visible response), this is measured server-side via `telemetry.ts`'s structured logs (timestamp at request-in, timestamp at MP-request-issued inside the `after()` callback), not via client-side load-test tooling, which can only see the earlier `204`/JSON response.
22. A replayed queued event (M2) carrying a capture-time `client_id`/`ga_session_id`/`ga_session_number` with a missing or invalid HMAC signature is rejected, and produces zero outbound MP calls — the cookie remains authoritative for live events; only signed capture-time identity is trusted on the replay path. Verified at the network/integration level (mock MP server), not unit-only.
23. Calling `createGa4Relay(config)` with a missing `apiSecret`/`tokenSecret`, or with rate limiting enabled while `store` is the in-memory implementation and `NODE_ENV === 'production'`, throws at construction time rather than silently degrading.
24. (M2) A replayed queued event whose signed `client_id` does not match the `client_id` in the browser's current live cookie is rejected (zero outbound MP calls), even if the signature itself is valid — a stale/foreign identity snapshot can never override the live cookie.
25. A rate-limited request (threshold exceeded on the Upstash-backed `Store`) receives `429` with a `Retry-After`-equivalent hint; the same request against the in-memory dev `Store` is documented as single-process-only and not asserted as a production-equivalent result.
26. (M2) **(three-class classification)** A queued event rejected with a genuinely permanent error (400/403) is dropped from the IndexedDB queue and not resent. A queued event rejected with 401 (expired/missing token) **remains queued** and is retried only from a page-load context (never from a Background-Sync/SW-only flush, which has no token-refresh path) — verified by simulating a 401 from a tab-closed Background Sync flush and asserting the record survives in the queue rather than being dropped. A queued event that failed with a retryable condition (429/5xx/network/offline) remains queued and is retried per the backoff policy from any context.
27. (M2) The service worker registered by `create-service-worker-handler.ts` reports `registration.scope` equal to the installer-configured scope (not narrowed to the route's own directory), verified via the `Service-Worker-Allowed` response header plus a matching `scope` option at `register()`.
28. (M2) Flipping the kill-switch config causes the **client SDK** (main thread, on next page load) to call `registration.unregister()` directly — not solely relying on the SW's own `activate` handler, which does not re-run on an unchanged script.
29. Rate limiting keys on the token's per-issuance `kid` claim (1.5) — not IP, which false-positives CGNAT/corporate NAT, and not `client_id`/origin alone, which are attacker-obtainable or shared site-wide (a token is obtainable by loading the page, same as `client_id`; the `kid` key's advantage over IP is NAT-safety, not rotation-resistance — stated honestly, not as an anti-abuse silver bullet). Default threshold/window are configurable, ship with a documented default (e.g. 120 events/min per `kid`), and load tests (AC18) either use a distinct per-virtual-user `kid` per simulated browser or an explicit test-only threshold override — the default is never sized to block a legitimate single-session load test.
30. `ip_override` in the outbound MP payload results in a populated GA4 geo dimension (country/region) for a known-IP test request — not just correct *sourcing* (AC5) but confirmed *effect*, verified against a **real staging GA4 property**, not a mock server (a mock cannot tell you whether real GA4 populates the dimension — that's exactly the schema-only blindness this AC exists to defeat).
31. A request carrying an explicit `analytics_storage: 'denied'` transition, sent with an existing `client_id`/session cookie already present, receives `Set-Cookie` deletion headers (`Max-Age=0`, matching `Domain`/`Path`) for the **`client_id` and session cookies specifically** (the strictly-necessary token cookie from 1.5 is untouched) — those two cookies are absent from the browser's jar after this response. An absent-consent-object request (no signal at all, can't distinguish withdrawal from first visit) does not attempt deletion.
32. When the client SDK observes an explicit denial signal, the IndexedDB queue is purged (record count is 0 immediately after), removing any previously queued records that carried persistent identifiers.
33. A queued record captured under granted consent, whose *current* consent at flush time has since become denied, is not forwarded (zero outbound MP calls) and is dropped from the queue — current-consent-at-flush-time overrides capture-time consent.

**Nice-to-have (explicitly deferred past v1):**
19. Meta CAPI `event_id` dedup parity with the browser Pixel's `eventID`.
20. At-least-once delivery guarantee across a function crash (requires a durable queue such as QStash/Vercel Queues — `after()`/`waitUntil()` work is cancelled on function timeout and is not durable across instance death; v1 delivery is explicitly best-effort and this must be documented, not silently assumed).
21. `?debug=1` inline MP validation response in the collect endpoint itself.

## Implementation Steps

### M0 — Spikes (block M1 start on outcomes; ~2-4 days for 0.1/0.2/0.3; 0.4 runs as a background clock, see below)
0.1. **Fidelity spike**: send ~100 representative events via MP v2 to a scratch GA4 property; compare Realtime/Traffic-acquisition/Engagement reports against a `gtag`-instrumented control page. Must explicitly measure, not just "compare": (a) whether `engagement_time_msec`/`session_id` presence is required for Realtime visibility — MP's `/debug/mp/collect` returns an empty `validationMessages` array even when these are missing, so this is the one failure mode the standard validation gate (AC1) does not catch; (b) whether device/browser/OS dimensions survive MP v2 without a forwarded user-agent, and what forwarding it correctly requires; (c) whether synthesizing `session_start`/`first_visit` from the relay's own session cookie (which already tracks `ga_session_number`) can recover part of the fidelity gap cheaply, since the relay already owns the data needed to emit them; (d) whether `ip_override` actually populates GA4's geo (country/region) dimensions, not just whether it's sourced correctly (AC5 vs AC30 — sourcing and effect are separate failure modes, and `/debug/mp/collect` catches neither). Note on timeline: (a)/(d) are visible in Realtime within minutes; Traffic-acquisition/Engagement report settling can take up to 48h, so the M0 window may need to extend a few days past 0.2/0.3's completion for those specific checks to fully settle — this is a data-latency constraint, not a scheduling slip.

Document in `docs/spikes/sw-beacon-capture.md`.
0.3. **Google-native first-party mode check**: verify whether Google's own first-party mode for Google tags is usable on Vercel deployments. If yes, scope the client SDK's script-loading concern (not proxying/rewriting) around it rather than building parallel plumbing. Document in `docs/spikes/first-party-mode.md`. (Scope note: this spike informs M3.1 script-proxying decisions only — it has no bearing on the Edge-vs-Node runtime choice in M1.7, which is decided independently on latency/library-compatibility grounds.)
0.4. **Safari ITP cookie-longevity observation**: starts on M0 day 1 as a background clock (an 8+ day real-Safari test cannot fit inside the 2-4 day M0 window for 0.1-0.3), reporting results during M1 rather than gating M0 exit. ### M1 — Core relay (must-have v1), packaged as config-injected factories

Directory shape (package, not app-local files) — full listing, corrected to include every module created across M1/M2 (a prior revision's listing omitted six of these):

packages/ga4-relay/src/

            create-relay.ts, create-collect-handler.ts, create-debug-handler.ts,
            create-service-worker-handler.ts, dedupe-store.ts (M2), telemetry.ts
  client/   client-sdk.ts (browser-bundled, see 1.13)
  sw/       service-worker script source (browser-bundled, served via create-service-worker-handler.ts, M2)

`apps/demo/` in this repo is a reference installation only, not the product.

1.0. **(M10) Scaffolding, must precede 1.1** — workspace init (pnpm workspaces), `packages/ga4-relay` package config with a bundler (`tsup`/`esbuild`) for the two browser artifacts (`client/client-sdk.ts`, `sw/` script — server-side TS compilation alone won't produce deployable browser bundles for these), the test harness (Vitest for unit/integration, Playwright for e2e, a mock MP server fixture that AC5/AC22 and most integration tests depend on — AC30 is the one exception and requires a real staging GA4 property instead, not the mock), and `apps/demo/` as a minimal Next.js app that installs the package. No implementation step below this one is startable against the actual (currently empty) repo state without this step existing first.

1.1. `mp-client.ts` — builds and POSTs GA4 MP v2 payloads to `https://www.google-analytics.com/mp/collect` (configurable region endpoint via `config.region`), and a validation-mode variant hitting `/debug/mp/collect`.
1.2. `cookies.ts` — read/write first-party `client_id` cookie (`Secure; HttpOnly; SameSite=Lax; Max-Age=63072000`, `Domain` configurable in `config` for apex/`www` and multi-subdomain installs — no default assumed, since guessing wrong silently splits identity across hostnames; the deployment guide states explicitly that every origin covered by the configured cookie `Domain` must also be present in the Origin allowlist (1.7), since a cookie scoped wider than the allowlist would let a subdomain read/send the identifier without being able to complete a request — the two are configured together, not independently). Value is **version-prefixed** (`v1:<raw>`) where `<raw>` is *either* a freshly minted UUID (no existing `_ga` cookie, AC2) *or* the `<random>.<timestamp>` string read from an existing `_ga` cookie (AC3) — the `v1:` prefix wraps whichever raw value applies and exists purely for future format migration; it does not imply the raw value is itself UUID-shaped. **The `v1:` prefix is storage-only and is always stripped before the raw value enters any outbound MP payload or the identity JSON response (1.7)** — otherwise GA4 would receive `v1:<random>.<timestamp>` and AC3's entire purpose (joining server-relayed events with gtag-collected data on a matching `client_id`) would silently fail. `_ga` cookie parity read, and session cookie (30-min sliding expiry, `ga_session_id` + `ga_session_number`).
1.3. `consent.ts` — parses Consent Mode v2 signals from the request body; **an absent/missing consent object is treated as fully denied** (AC6a, default-deny — no implicit grant). Under denial, the request is short-circuited before 1.7 does anything else: no cookie *value* is used for identity, no MP call is made, and **no identity/signature is computed or returned in the response body** (AC6) — a cookie's mere *presence* is still checked, solely to decide whether the deletion branch below applies — this is a hard branch in the collect handler, not a downstream filter, so there is no code path where 1.7's identity JSON can be reached under denial. **Consent-transition sweep (per Critic round-2 finding — the same blind spot that produced C1 recurs whenever state outlives the moment consent is checked, so this is one deliberate pass covering everywhere it can recur, not three separate patches):**
- **Cookie deletion on explicit denial while a relay cookie exists** (AC31, scoped to the `client_id`/session cookies only — the token cookie from 1.5 is deliberately consent-independent/strictly-necessary and is never deleted by this branch): when a request carries an explicit `analytics_storage: 'denied'` signal *and* the request already has a `client_id`/session cookie set (i.e. this is a withdrawal, not a first visit), the collect handler emits `Set-Cookie` with `Max-Age=0`, **matching the exact `Domain` and `Path` used when the cookie was originally set (1.2)** — a deletion header with a mismatched `Domain`/`Path` silently no-ops rather than deleting, so the values must be read from the same `config.cookieDomain` used at set-time, not re-derived. This is necessary specifically because the cookie is `HttpOnly` — the host site's CMP runs in JavaScript and structurally cannot delete it itself; the relay is the only component that can. A `Max-Age=0` deletion header is not a *persistent* `Set-Cookie`, so it does not violate AC6's "no persistent `Set-Cookie`" bar — AC6 is worded to make that distinction explicit rather than have the three-surface test flag correct deletion behavior as a failure. (Absent-consent-object requests, which have no way to know if this is a withdrawal vs. a first visit, do not attempt deletion — only an explicit `'denied'` signal triggers it.)
- **Queue purge on denial** (AC32): the client SDK purges the entire IndexedDB queue when it observes an explicit denial signal, since queued records hold persistent identifiers (`client_id`/`ga_session_id`) that withdrawal should clear from client storage, not just suppress from forwarding.
- **Flush-time consent policy** (AC33): a queued record's *capture-time* consent governs whether it was ever legitimately captured (an event captured under denial should never exist in the queue in the first place, per the short-circuit above); *current* consent at flush time is checked additionally and suppresses the flush on denial — belt-and-braces, drop on either signal being denied, never forward on an ambiguous read.
Gates cookie issuance, identifier forwarding, and response-body identity per AC6/AC6a. Note: this module only *consumes* signals — it does not own producing correct signals from the host site's CMP; the package README must document the contract the installer's CMP integration must satisfy (this is a documentation/integration responsibility of the installer, called out explicitly rather than left implicit).
1.4. `validate.ts` — enforces MP limits (≤25 events/request, ≤25 params/event, name ≤40 chars, value ≤100 chars, **request body ≤130KB per MP's documented limit — checked independently of event/param count, since batch-splitting on count alone doesn't bound payload size if individual param values are large**, batch splitting), a PII deny-list (email/phone regex + configurable blocked param names), **and explicit query-string scrubbing on `page_location`/`page_referrer`** (the highest-frequency real-world GA4 PII leak vector), plus a stated policy for `user_id` (rejected unless pre-hashed by the installer).
1.5. `token.ts` — HMAC-signed token binding origin + a random per-issuance `kid` subject claim (minted at issuance, not derived from anything the client controls) + short TTL (~15 min). **Reissue condition, stated explicitly since it determines whether AC29's rate-limit counter can ever accumulate**: `withGa4Token` mints a fresh token (new `kid`, resetting the counter) only when the incoming request has no valid, unexpired token cookie — a request presenting a still-valid token is passed through unchanged, keeping the same `kid` for the remainder of its ~15-min TTL, so AC25's threshold is reachable within one token's lifetime rather than being reset on every request. Issued as a `Secure; HttpOnly; SameSite=Lax` cookie (`SameSite=Lax` is sufficient — it is not sent on cross-site POST, so the double-submit anti-CSRF property is preserved; `HttpOnly` because the client never needs to read it, it rides automatically). Exported as a composable `withGa4Token(config)` middleware function the installer calls from their own root `middleware.ts` — **a Next.js app can only have one root `middleware.ts`, so the package cannot ship its own file**; ships a recommended `matcher` scoped to the collect/debug/SW routes so it doesn't add Edge latency to every request in the host app. This cookie is treated as **strictly necessary** (request provenance/anti-abuse, not tracking) and is therefore set independent of `analytics_storage` consent — documented explicitly as a deliberate position, not an oversight, since Principle 3 makes every consent-adjacent decision worth stating rather than leaving implicit. Verification in the collect handler reads the cookie (available automatically on both `sendBeacon` and `fetch keepalive` requests, avoiding the header-unavailability problem of `sendBeacon`).
1.6. `store.ts` — a `Store` interface (`incr(key, ttlMs)`, `get(key)`, `setNX(key, value, ttlMs)` — **TTL is a parameter on every write method**, not a separate concern, since both the rate-limit window and the 48h dedupe TTL need to express expiry through the same interface) with two implementations shipped in M1: an in-memory one **explicitly labeled development-only, not a production guarantee** (documented loudly — multi-instance Vercel deployments do not share memory, so this must never be claimed as a real control), and an Upstash-Redis-backed one. Rate limiting in production **requires** the Upstash implementation to be configured; this is stated as a deployment requirement, not silently assumed to work with defaults, and enforced at construction time (see 1.12/AC23). **Deployment requirement**: the Upstash database must be provisioned in the same region as (or the region nearest to) the Vercel function deployment — a cross-region round trip can consume most of AC17's 50ms budget by itself; this is stated in the deployment guide as a concrete requirement, not left to be discovered. Expected steady-state cost: 1 `Store` operation per event for rate limiting (M1), a 2nd for dedupe once M2 lands — sized against the installer's expected traffic and Upstash tier in the deployment guide. **Store-unavailability policy stated explicitly**: for rate limiting, a `Store` error fails open (traffic is allowed through rather than the site going dark — an accepted risk, stated as such, not a silent gap); for dedupe (M2, 2.1), a `Store` error fails **closed on replays** — a replayed event is dropped, never forwarded, when the dedupe store can't be reached, because forwarding an unverifiable replay is exactly the double-counting Principle 5 exists to prevent. The same interface is reused by M2's dedupe store — no new abstraction needed later.
1.7. `create-collect-handler.ts` — Node runtime Route Handler **factory** (`createCollectHandler(config)`) so the installer mounts it at any path they choose (satisfies the ad-blocker path-configurability mitigation below — a hardcoded path cannot). Validates token(cookie)+Origin+consent+payload. **Under `analytics_storage: 'denied'` or an absent consent object (AC6/AC6a), returns `204` with no body and stops — no MP call, no identity payload; the branches below only execute when consent is granted. Exception: an explicit `'denied'` signal (not an absent one) accompanied by an existing relay cookie on the request triggers 1.3's cookie-deletion branch (`Max-Age=0` on `client_id`/session cookies, AC31) before the `204` is returned — this is a deletion header, not a persistent `Set-Cookie`, so AC6's "no persistent `Set-Cookie`" bar still holds.** On grant: sets cookies, **returns a small JSON body** (not bare `204`) containing the resolved `client_id`/`ga_session_id`/`ga_session_number` **plus an HMAC signature of that full triple and its `issued_at` timestamp (using the same `tokenSecret` as 1.5), with a marker that it is a server-issued capture snapshot** — a replay whose `issued_at` is older than the 48h queue/dedupe TTL (AC13, 2.1) is rejected regardless of signature validity, bounding how long a genuinely-issued identity snapshot can be replayed. On the **replay path** (2.2/AC22), the signature is verified **and** the signed `client_id` must equal the `client_id` in the browser's current live cookie — the signature only ever authorizes restoring `ga_session_id`/`ga_session_number`/capture timestamp from a rolled-over session, never a change of `client_id`; a replay whose signed `client_id` doesn't match the live cookie is rejected and the event dropped (accepted tradeoff: a user who clears cookies between capture and flush loses that queued event rather than having it silently misattributed). On **live** (non-replayed) requests, the cookie remains the sole source of truth for identity. This resolves the identity/queue defect from the first Architect review and the replay-spoofing hole from the second Architect review, and closes the cross-user-stitching gap flagged by Critic round one (signature is scoped to session-continuity, never an identity-override bearer token). **Error contract** (backs M6/retry classification in 2.2, three classes not two): 400 (validation failure) and 403 (origin) carry `{ retryable: false }` — genuinely permanent, drop. 401 (bad/expired/missing token) carries `{ retryable: 'needs-token-refresh' }` — **not permanent**: the SW's Background Sync flush (2.3) can run long after the ~15-min token TTL (1.5) has expired with no way to refresh it itself, so treating 401 as permanent would silently delete exactly the tab-closed offline events the resilience layer exists to save; these records stay queued and are retried only from a page-load context, where `withGa4Token` middleware reissues a fresh token cookie. 429 carries `{ retryable: true, retryAfterMs }`. 5xx/network failure is retryable with no body assumed. Forwards to MP inside `next/server` `after()`. Edge vs. Node runtime is decided directly on cold-start latency (AC17/AC18) vs. Node library compatibility for HMAC/body parsing — **not** gated on M0.3 (M0.3 investigates Google's first-party mode for `gtag`, which has no bearing on this runtime choice; that cross-wiring from the draft is corrected here). `maxDuration` explicitly set (~10s, not the 300s default). **Package-level kill switch**: `config.enabled` (default `true`), sourced from an env var — flipping it requires a redeploy to take effect (Vercel binds env vars at deploy/build time, not live; stated accurately rather than claiming an instant flip that doesn't exist) — makes the handler a no-op passthrough when `false`, but **returns `{ enabled: false }` as a JSON body (not bare `204`)** specifically so AC28 is satisfiable: the SDK must be able to distinguish "relay disabled → unregister the SW" from "consent denied → leave the SW registered," and a bodyless response can't carry that distinction. Delivery channel to the client SDK: read from 1.7's own response on the first (identity-resolving) collect call of each page load — piggybacks on an existing round trip. Consent-denied page loads never reach this branch (1.3's short-circuit returns bare `204` first) — acceptable for *event sending* (both cases already send nothing) but not for the SW registration decision, which is exactly why the disabled path needs its own distinguishable body while the denied path doesn't.
1.8. `create-debug-handler.ts` — factory for a passthrough to MP's validation endpoint for local/staging testing.
1.9. `client-sdk.ts` (+ small public bundle) — resolves capture-time identity **once per page load**: the **first** collect call of a page load always goes via `fetch(..., {keepalive:true})` (never `sendBeacon`, whose response body is inaccessible by design — `sendBeacon`-first would leave identity permanently unresolved), reads the JSON body (`client_id`/`ga_session_id` + signature) from 1.7, and caches it in memory for the page lifetime. This has no downside: the first event of a page load is a load-time `page_view`, not an unload event, so it never needed `sendBeacon`'s unload guarantee. Every **subsequent** event on that page carries the cached identity + signature and follows the normal transport chain: `navigator.sendBeacon` first (this is where the unload guarantee matters and is now available, since identity is already cached) → `fetch(..., {keepalive:true})` fallback if `sendBeacon` returns `false` (queue full/payload too large) → IndexedDB queue (M2) if both fail or offline. No queueing yet in M1 (added M2). Respects `document.prerendering`; ignores `popstate`-only soft-nav duplicates. **Bundle size budget**: the client SDK's gzipped bundle is capped at 5KB in v1 (CI-enforced via a bundle-size check) — it ships on every page of the host site, so its cost is a first-class constraint, not an afterthought; if the transport chain, queue, retry classification, and consent-transition logic can't fit, the budget is revisited explicitly (documented escape hatch) rather than silently exceeded.
1.10. `event.ts` — normalized internal event shape used by the client SDK and collect handler, so M3.2's destination-fan-out additivity claim has an actual home instead of being aspirational.
1.11. `telemetry.ts` — structured log emission for the counters required in Verification Steps (forwarded/dropped-by-reason/retried/deduped), since "counters" on stateless Vercel means log lines + external aggregation, not in-process state.
1.12. Config surface: `createGa4Relay(config)` takes an explicit config object (`measurementId`, `apiSecret`, `region`, `tokenSecret`, `allowedOrigins`, `store`, rate-limit thresholds, `debugMode`) that **defaults from env vars but is never read ambiently inside modules** — this is the seam (per Architect synthesis) that makes Option C's "layer on later without rearchitecting" claim actually true, without itself being tenant-resolution code. `createGa4Relay(config)` **validates at construction and throws** rather than degrading silently: missing `apiSecret`/`tokenSecret`, or rate limiting enabled with the in-memory `store` while `process.env.NODE_ENV === 'production'` (AC23) — boot-time failure beats a defanged-but-passing control. Guardrail restated: v1 ships **one tenant, no auth, no billing, no domain provisioning, no sandboxed user-code execution** — the prohibition targets scope and unsafe code execution, not the config-object seam itself (correction to the draft's "no DB-backed config" wording, which over-reached and forbade a future declarative, versioned, non-sandboxed event-mapping file).
1.13. **Client/server entrypoint boundary** (closes the gap where AC8's bundle-grep was the *only* control against secret leakage — a detection control, not a prevention one): `package.json` `exports` map declares distinct `./server` (everything under `src/server/`), `./client` (`src/client/client-sdk.ts` + `src/shared/event.ts` only), and `./sw` (the service worker script) entrypoints. Nothing reachable from `./client` or `./sw` may import `token.ts`, `mp-client.ts`, `store.ts`, or any module that touches `apiSecret`/`tokenSecret` — enforced by an ESLint import-boundary rule in CI (build-time prevention) in addition to AC8's grep (runtime detection, kept as defense-in-depth).

### M2 — Resilience layer
2.1. `dedupe-store.ts` — reuses the `Store` interface from 1.6 (Upstash-Redis-backed in production), keyed on client-generated `event_id`, 48h TTL (ships in the same PR as 2.2, per Principle 5 / Pre-mortem #2 — **CI enforcement of this rule**: a repo-level check that the PR diff touching `client-sdk.ts`'s queue/retry logic also touches `dedupe-store.ts` and its test file, not merely a stated convention). Because M1 already shipped the `Store` interface, this is a second implementation behind an existing seam, not a new abstraction — the apparent "stateless-first vs. needs Redis" tension is resolved: dedupe is inherently cross-request shared state and was always the "proven necessary" case Principle 1 anticipates. Data retention: the dedupe store holds only opaque `event_id` values (client-generated UUIDs, not personal data) with a 48h TTL — stated explicitly in the deployment guide so this doesn't need to be inferred.
2.2. Extend `client-sdk.ts` — bounded FIFO IndexedDB queue (max 500 events, drop-oldest, **schema-versioned records** so a future field addition — e.g. the `ga_session_number`/signature fields added in this revision — can migrate old queued records rather than silently misreading them), fixed DB/store name across versions (never recreated), flush on `online` and next page load. **Every queued record stores the capture-time `client_id`/`ga_session_id`/`ga_session_number` plus the HMAC signature returned in 1.7's JSON response**, not whatever the cookie holds at flush time (AC6b) — this is the fix for the identity-binding defect, applied at the point events are written to the queue. On flush, the collect handler verifies the signature **and** that the signed `client_id` matches the live cookie before trusting the replayed identity; a mis-signed or cookie-mismatched replay is rejected outright (AC22/AC24), closing the spoofing/stitching path the identity fix would otherwise open. **Retry classification, three classes** (per 1.7's error contract): a `{ retryable: false }` response (400/403) drops the record from the queue immediately and increments a `dropped-permanent` telemetry counter — it is never resent. A `{ retryable: 'needs-token-refresh' }` response (401) stays queued, is **not** retried from a Background-Sync/SW context (no token-refresh path exists there — 2.3), and is retried only on the next page-load flush after `withGa4Token` middleware has reissued a fresh token cookie (AC26). A `{ retryable: true }` response (429) or a network failure/offline condition keeps the record queued and retries with exponential backoff, from any context. **Consent transitions** (1.3's sweep, applied client-side): observing an explicit denial signal purges the entire queue (AC32) — queued records hold persistent identifiers that withdrawal should clear from client storage, not just suppress from forwarding. On flush, the SDK re-checks *current* consent (not only the capture-time consent stored on the record) and suppresses forwarding on denial, dropping the record rather than sending it (AC33) — capture-time consent governs whether the record should ever have existed; current consent additionally gates the send. **Multi-tab**: the queue is a single shared IndexedDB store across tabs; concurrent flushes from multiple tabs may each attempt the same record, but server-side dedupe (2.1) absorbs the resulting duplicate — no client-side tab-coordination (`navigator.locks`, leader election) is implemented in v1, since it would only be an optimization, not a correctness requirement, given dedupe already exists.
2.3. `create-service-worker-handler.ts` — factory for a Route Handler serving the SW script as `text/javascript` with `Cache-Control: no-cache` (an npm package cannot write into a consumer's `public/`, so a served route, not a static file, is the only distributable option). **Response includes `Service-Worker-Allowed: <configured scope>` (default `/`), and the client SDK's `register()` call passes the matching `scope` option** — without this, a nested installer-chosen path (e.g. `/api/ga4/sw.js`, per the ad-blocker-evasion guidance in the Risks and Mitigations table) would default its scope to that path's own directory and never observe a page navigation, silently defeating the SW (AC27). Background Sync registration flushes the IndexedDB queue even after tab close (Chromium-only; other browsers rely on flush-on-load/online from 2.2); no HTML/asset caching (fetch handler untouched for everything except analytics retries). **Kill switch is primarily main-thread**: the client SDK checks the kill-switch config on every page load and calls `registration.unregister()` directly if disabled (AC28) — the SW's own `activate` handler also checks and self-unregisters as a secondary path, but `activate` does not re-run on an unchanged script, so it cannot be the sole mechanism.
2.4. Rate limiter (1.6) already targets the `Store` interface; production deployments configure the Upstash implementation — no rewiring needed in M2.

### M3 — Deferred / explicitly out of v1 (documented as non-goals, not silently dropped)
3.1. First-party script proxying for the `gtag.js` loader via the *supported* `server_container_url`/`transport_url` config (never response-body regex rewriting of Google's bundle) — contingent on M0.3 findings.
3.2. Non-GA4 destination fan-out (Meta CAPI, etc.) — internal event shape from M1 kept normalized so this is additive later, but zero adapters ship in v1/v2.
3.3. Multi-tenant SaaS mode (Option C) — revisit only after Option A's core is proven; requires a new secret-custody and data-processor analysis before any work starts.
3.4. Durable at-least-once delivery via QStash/Vercel Queues — only if M1's best-effort delivery proves insufficient in practice.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| MP returns 2xx on malformed/rejected payloads — failures are invisible | All integration tests run against `/debug/mp/collect`; treat any non-empty `validationMessages` as a test failure (AC1). |
| Retry without dedupe double-counts events, corrupting customer analytics silently | Principle 5 + Pre-mortem #2: retry and dedupe ship in the same milestone/PR, enforced by CI test coverage, not convention alone. |
| Consent Mode v2 gating bug leaks a persistent identifier under denial (GDPR exposure) | Pre-mortem #3: standing network-level contract test on every PR touching the collect path, not just consent-specific PRs. |
| Open write endpoint into a customer's GA4 property (spoofed/abusive hits) | Signed short-TTL origin-bound token with a per-issuance `kid` (must — this is request provenance, not visitor authentication: any client can obtain a token by loading the page, same posture as stock client-side GA4/`gtag`, per Requirements Summary) + Origin allowlist (hygiene, since Origin is forgeable by non-browser clients) + rate limiting keyed on the token's `kid` via the `Store` interface — **real only when the Upstash implementation is configured**; the M1-default in-memory `Store` is explicitly documented as dev-only and enforced at construction time (AC23), never silently relied on in production. |
| A client replays a fabricated **or exfiltrated** capture-time `client_id`/`ga_session_id`/`ga_session_number` on the offline-queue flush path, poisoning attribution or stitching sessions across users | Capture-time identity is HMAC-signed (closes fabrication, AC22) **and** the replay path additionally requires the signed `client_id` to match the browser's current live cookie (closes cross-user stitching via an exfiltrated snapshot, AC24) — the signature only ever authorizes restoring session continuity, never overriding identity. Bounded to 48h by `issued_at` (see 1.7). |
| Consent-denied requests still expose identity via the collect response body (not just the cookie) | 1.3/1.7 short-circuit under denial/absent-consent before any identity is computed — `204`, no body, no cookie, no MP call (AC6/AC6a, three-surface network-level assertion). |
| A two-year `HttpOnly` `client_id` cookie survives consent withdrawal indefinitely, because the host CMP runs in JS and structurally cannot delete an `HttpOnly` cookie itself | Explicit `analytics_storage: 'denied'` transition (with a relay cookie present) triggers a `Max-Age=0` deletion `Set-Cookie` from the relay — the only component that can (AC31). |
| Persistent identifiers already sitting in the IndexedDB queue survive consent withdrawal, and a queued record's stale capture-time consent could authorize a forward that current consent forbids | Explicit denial purges the entire queue client-side (AC32); flush additionally re-checks current consent and drops rather than forwards on denial, independent of capture-time consent (AC33). |
| Client-supplied `x-forwarded-for` is spoofable and must never feed `ip_override` | AC5 requires the platform-set `x-vercel-forwarded-for` header exclusively; a mock-MP-server test asserts no fallback to client-controllable headers. |
| Capture-time identity lost when an offline-queued event is flushed hours later under a different/new session cookie | Collect handler returns capture-time `client_id`/`ga_session_id` in its JSON response (1.7); client SDK stores it with the queued record and replays it at flush time (2.2), verified by AC6b. |
| Token-in-page-HTML conflicts with Next.js static rendering (token expires for every static visitor, or forces the host app off static rendering) | Token issued as a cookie by the installer's own root `middleware.ts` calling the package's composable `withGa4Token(config)` (a Next.js app can only have one root middleware file, so the package cannot ship its own) — runs per-request regardless of page rendering mode, instead of server-rendered into HTML. |
| PII forwarded to GA4 violates Google's ToS and risks property termination | `packages/ga4-relay/src/server/validate.ts` deny-list (including `page_location`/`page_referrer` query scrubbing and the `user_id` policy) enforced server-side before every outbound call, not just documented as a client-side convention. |
| Scope creep toward a full sGTM config engine/UI (Option B) | Explicit non-goal in README; v1 config is an explicit, injected config object (env-var-defaulted) — no sandboxed user-code execution, no template marketplace. A declarative, non-sandboxed event-mapping file is not ruled out, only a code-execution engine is (see 1.12). |
| Scope creep toward multi-tenancy (Option C) | v1 ships one tenant, no auth, no billing, no domain provisioning — but the explicit config-object seam (1.12) is deliberately kept so a future tenant-resolution layer is additive, not a rearchitecture. |
| Ad-blocker filter lists add rules for a well-known relay path within weeks | Collect path is configurable per-deployment rather than a single well-known path shared across all installs; documentation never claims "unblockable." |
| Safari ITP caps CNAME-cloaked cookies at 7 days | Genuinely same-origin cookie issuance (Option A's core advantage over a CNAME-based vendor) — M0.4 starts an 8+ day real-Safari observation on day 1 of M0, reporting during M1; the advantage is stated as mechanism-derived-but-unvalidated in the ADR until it reports. |
| Rate limiting appears to work in tests but is a no-op in production (in-memory counters don't survive Vercel's multi-instance/cold-start model) | `Store` interface (1.6) ships two implementations from M1: in-memory labeled dev-only, Upstash for production; tests exercise both and the production deployment guide states Upstash configuration is required, not optional, for rate limiting to function. |
| Absent/missing consent signal treated as implicit grant | AC6a: default-deny on missing consent object, asserted at the network level in the same standing contract test as AC6. |
| `waitUntil`/`after()` work is cancelled on function timeout and isn't durable across instance death | v1 documentation states delivery is best-effort; at-least-once is an explicit M3 dependency on a durable queue, never silently assumed — **accepted risk, not a mitigated one**. |
| Installer follows the ad-blocker path-configurability guidance (this table, "Ad-blocker filter lists" row), mounts the SW at a nested path, and its scope silently narrows to that path's own directory — SW never sees a navigation, every SW-related AC still passes | `Service-Worker-Allowed` header + matching `register({scope})` (2.3/AC27) — scope is explicit, not left to browser default behavior. |
| The SW's only kill mechanism (`activate`) doesn't re-run on an unchanged script, so an emergency disable silently fails to disable anything | Kill switch is primarily main-thread (`registration.unregister()` on page load, AC28), with the SW's `activate` check kept only as a secondary path. |
| Retry queue can't distinguish "permanently invalid" from "should retry," wasting requests and Upstash reads on events that will never succeed | 1.7's three-class error contract (`retryable: false / 'needs-token-refresh' / true`) + 2.2's matching classification — AC26. |
| A tab-closed Background Sync flush hits an expired 15-min token (401) and, if misclassified as permanent, silently deletes exactly the highest-value offline-queued events the resilience layer exists to save | 401 is its own retry class, not lumped with 400/403: the record stays queued and is retried only from a page-load context where the token is refreshed — never dropped for a credential reason alone (AC26). |
| Cross-region Upstash round trip silently eats most of the 50ms latency budget | Deployment guide states region colocation as a requirement (1.6); AC17 explicitly includes the Upstash hop in its measured budget rather than excluding it. |

## Verification Steps (expanded test plan)

**Unit** (all in `packages/ga4-relay/src/server/` unless noted)
- `validate.ts`: MP limit enforcement (event name/param length, param count, batch splitting, body size), PII deny-list matches (including `page_location`/`page_referrer` scrubbing).
- `token.ts`: HMAC sign/verify, `kid` uniqueness, TTL expiry rejection, capture-identity signature verify/reject (AC22).
- `cookies.ts`: `client_id` mint vs. `_ga`-cookie-derived reuse, session sliding-window boundary (5 min vs. 31 min cases from AC4), version-prefix parsing (and that the `v1:` prefix is stripped before the value is used in any outbound MP payload — see 1.2).
- `consent.ts`: all four Consent Mode v2 signal combinations plus the absent-object case gate correctly in isolation; deletion-vs-no-deletion branch (explicit denial + existing cookie vs. absent signal).
- `create-relay.ts`: constructor validation throws for missing secrets / in-memory store in production (AC23).

**Integration**
- Collect route against `/debug/mp/collect`: AC1, AC10, AC11 (validation empty, batch split, name rejected-not-truncated) — plus the M0.1-derived assertion that `engagement_time_msec`/`session_id` are always present, since `/debug/mp/collect` alone won't catch their absence.
- Mock-MP-server tests: AC5 (`ip_override` sourcing from `x-vercel-forwarded-for` only, explicit negative test that a spoofed client `x-forwarded-for` is ignored), AC9 (dedupe, once M2 lands), AC22/AC24 (replay path — valid signature + matching cookie accepted; invalid signature rejected; valid signature but mismatched `client_id` rejected — three distinct cases, not unit-only).
- **Real-staging-property test** (not mock — AC30 specifically requires this, since a mock can't prove MP actually honors the field): `ip_override` populates an actual geo dimension.
- Origin/token auth: AC7, AC8 (403/401 paths, canary-value bundle grep, ESLint import-boundary check per 1.13) plus AC6/AC6a's three-surface assertion (no cookie, no body, no MP call) run at this layer too, not only E2E. Token verification tested via the middleware-issued cookie path specifically (not a header), matching 1.5's actual transport.
- Rate limiter: tested against **both** `Store` implementations — in-memory (single-process behavior only, explicitly not treated as a production-equivalence test) and Upstash (the production-equivalent test that actually exercises cross-instance-shared counters); AC29 (key is the token-bound identity, not IP or `client_id`); threshold breach returns 429 (AC25) and the client backs off; explicit fail-open test (Store made unreachable → request still succeeds).
- Retry classification (AC26): mock collect responses across all three classes (400/403 permanent-drop; 401 stays-queued-needs-refresh, explicitly tested from a simulated Background-Sync/no-page context to confirm it survives rather than drops; 429/5xx/network retry-with-backoff) and assert queue drop-vs-retain behavior per class.

**E2E (Playwright)**
- AC2/AC3: cookie mint-and-reuse, `_ga` parity, across a real browser session.
- AC6/AC6a network-level consent contract test (Pre-mortem #3 mitigation), including the absent-consent-object default-deny case, **asserting all three surfaces** (no `Set-Cookie`, no identity in response body, no MP call) — runs on every PR touching `packages/ga4-relay/src/**`.
- AC6b: offline mid-session → wait past 30-min session window → online → assert flushed event carries capture-time session id, not a newly minted one (identity-binding regression test).
- AC31/AC32/AC33 (consent-transition sweep): grant → capture events → go offline → queue events → **revoke consent** → assert (a) relay cookies carry `Max-Age=0` deletion headers on the next request, (b) the IndexedDB queue is empty, (c) coming back online produces zero outbound MP calls for anything that was queued before the revoke.
- AC14/AC15/AC16/AC27/AC28 (M2): SW coexistence with an existing service worker, cache-control header, **registered scope equals configured scope (not narrowed)**, kill-switch flow verified via main-thread `unregister()` as primary (AC28) with the SW `activate` path as secondary.
- M0.2 spike test (cross-browser unload-beacon capture) re-run as a standing regression test once SW role is decided, not just a one-time spike.
- M2: offline queue → online flush timestamp correctness (AC12), 48h TTL drop (AC13), retry-classification behavior under real network conditions (AC26), multi-tab concurrent flush producing exactly one server-accepted event via dedupe (no client-side coordination assumed).

**Observability**
- Structured logs / counters for: events forwarded, events dropped (validation failure, PII match, rate-limited, consent-denied), retry attempts, dedupe hits — each as a distinct counter so a spike in "dropped" is distinguishable from a spike in "forwarded."
- Load test dashboard for AC17/AC18 (added latency, p99 relay latency) run before each milestone's release, not only once.
- Alert/kill-switch runbook: what a maintainer does when the "PII-blocked" or "consent-denied-forward" counters are non-zero unexpectedly.

## ADR

**Decision**: Build Option A — a single-tenant, stateless-first, first-party GA4 collection relay with a retry/dedupe-focused resilience layer — rather than a full sGTM clone (Option B) or a multi-tenant SaaS (Option C).

**Drivers**: Vercel's execution model rules out an always-on self-hosted sGTM deployment (disqualifying Option D within the stated Vercel constraint), not Option B on statelessness grounds — Option B is separately disqualified by the sandboxed-template-engine cost; GA4 MP's silent-failure behavior demanding validation-first design; compliance exposure from Consent Mode v2 and GA4's PII ban.

**Alternatives considered**: Option B (full sGTM clone) — rejected because the real multi-year cost is a sandboxed template-execution engine and template marketplace, not container statelessness (a container config snapshot can be fetched-and-cached per serverless instance same as sGTM caches it per boot). Option C (multi-tenant SaaS v1) — rejected as pulling in auth/billing/secret-custody/isolation work before the core value is proven, with no v1 benefit; deferred safely because M1's config-object seam (1.12) keeps that door open without a rearchitecture. Option D (self-host Google's official sGTM image, reverse-proxied same-origin) — the strongest alternative, delivering both Option A's first-party advantage and Option B's full engine; rejected primarily because it requires an always-on host in conflict with the stated Vercel-only constraint (dispositive on its own) — the resilience/retry/dedupe layer that's this project's real differentiator would still need building either way, though D would genuinely avoid rebuilding the MP-translation/cookie/consent/validation layer that sGTM already provides.

**Why chosen**: Option A delivers what stape.io customers actually pay for (first-party hosting, cookie longevity, resilience against ad-blockers/unload/offline conditions) without requiring Google's own tag-engine investment to be duplicated. Its core identity/session state lives in cookies, fitting Vercel naturally — though rate limiting and dedupe (both inherently cross-request shared state) require the Upstash `Store` implementation in production, which is a stated deployment requirement rather than a contradiction of the stateless-first principle.

**Consequences**: Lower data fidelity than real sGTM (no automatic `session_start`/`first_visit`/attribution/Google Signals) — must be measured (M0.1) and documented, not glossed over; M0.1 also checks whether the relay's own session cookie can cheaply synthesize part of this gap. No built-in multi-destination fan-out in v1/v2 (though M1 ships a normalized `event.ts` shape so this is additive, not a rewrite). Shipping as config-injected factory functions (per Architect review) is what makes a future move to multi-tenancy an additive config-resolution change rather than a rearchitecture — the remaining multi-tenancy cost is auth/billing/secret-custody/isolation, a real product decision, not plumbing. Delivery is best-effort in v1; at-least-once requires a durable queue dependency explicitly deferred to M3. Rate limiting is only a real production control when the Upstash `Store` implementation is configured — this is a stated deployment requirement, not a default guarantee. The cookie-longevity advantage over CNAME-based vendors is mechanism-derived from day one but carries an explicit "pending M0.4 empirical validation" qualifier until that 8-day observation reports. **Top-line success metric** (distinct from AC17/AC18, which measure the relay's own latency, not project value): once M2 ships, measure events captured via the resilience layer (retry/offline-queue/dedupe-verified deliveries) as a percentage of total events, against a baseline of client-side-only GA4 on the same traffic — this is the number that justifies the resilience layer's complexity, and M0.2's spike outcome is effectively a go/no-go on whether that number can be meaningful at all (see Pre-mortem #1).

**Follow-ups**: M0 spike outcomes may reshape M1 scope (SW role from 0.2; fidelity-driven event-shape changes from 0.1) — re-review this plan after M0 completes. The Edge-vs-Node runtime choice for the collect route is decided independently on latency/library-compatibility grounds (corrected from the draft's mis-wired dependency on M0.3). Multi-tenant SaaS (Option C), non-GA4 destination adapters, and `/g/collect` reimplementation remain explicitly out of scope pending a future decision, not silently abandoned. A declarative (non-sandboxed) event-mapping config file is not ruled out by the scope guardrails, only sandboxed user-code execution is.

## Assumptions Requiring User Confirmation (flagged for pending-approval review)

This plan was produced in non-interactive consensus mode; the following judgment calls were made using the Analyst's recommendations rather than direct user input, and should be confirmed or overridden before execution begins:
- Single-tenant, self-hosted deployment model (not multi-tenant SaaS) for v1.
- GA4 Measurement Protocol v2 as the wire protocol (not a `/g/collect` reimplementation).
- GA4-only in v1/v2 (no Meta CAPI or other destination fan-out).
- Service worker's role defaults to retry/resilience, promoted to capture-layer only if the M0.2 spike confirms reliability — not assumed reliable upfront.
- Ad-blocker evasion via script-proxying is treated as a deferred/optional goal (M3.1), not a hard v1 requirement, given its complexity and legal-exposure profile per the Analyst's review.
- Distribution as an installable package of config-injected factories (vs. app-local files) per Architect review — adds ~2-3 days of packaging work to M1 in exchange for the package actually being installable by someone other than the author, and for making the Option C deferral genuinely additive later.
- Production rate limiting and dedupe require configuring the Upstash `Store` implementation; the in-memory default is dev-only and must not be treated as a production control.
- Same-origin, same-Next.js-app deployment (not a separate subdomain/Vercel project) is treated as a hard requirement, since it's what the ADR's cookie-longevity/ITP advantage depends on.
